Arquitectura de Upload Seguro en Microservicios

Diseño implementado: el Gateway recibe y conserva los archivos físicos. Upload-MS se especializa en validar el contenido real del archivo.

Estado actual: recepción, validación inicial, UUID, cuarentena, comunicación TCP, validación de firma PDF, validación estructural con pdf-lib, eliminación de rechazados y movimiento de archivos estructuralmente válidos a verified/.

1. Entrada del archivo

Frontend
   |
   | HTTP multipart/form-data
   v
Gateway NestJS
   |
   v
Multer

El Gateway es el punto de entrada HTTP. Multer recibe el archivo mediante FileInterceptor.

Ejemplo: recepción del archivo

Este código crea el endpoint POST /upload. FileInterceptor('file') indica que Multer debe buscar dentro del formulario multipart un campo llamado file. Luego @UploadedFile() entrega al método el archivo recibido, incluyendo nombre original, MIME, tamaño y buffer.

// Define un endpoint HTTP POST /upload.
@Post()

// Intercepta el campo "file" del multipart/form-data.
// Multer procesa el archivo antes de ejecutar uploadFile().
@UseInterceptors(FileInterceptor('file'))

uploadFile(
  // Recupera el archivo procesado por Multer.
  // Express.Multer.File contiene originalname, mimetype,
  // size, buffer, etc.
  @UploadedFile() file: Express.Multer.File,
) {
  // A partir de aquí el Gateway puede validar
  // y procesar el archivo recibido.
}

2. Validación inicial en Gateway

Antes de escribir el archivo en disco, el Gateway realiza controles rápidos:

  • Usuario autenticado.
  • Tamaño máximo: 10 MB.
  • Extensión permitida.
  • MIME declarado permitido.

Allow-list inicial:

.pdf
.png
.jpg
.jpeg
.docx
.xlsx

Estas validaciones son preventivas, pero no confirman el contenido real.

Ejemplo: validación rápida en el Gateway

Esta capa no analiza todavía el contenido interno. Su objetivo es descartar rápidamente formatos que la aplicación no admite antes de escribirlos en disco.

// Obtiene la extensión del nombre original y la normaliza.
// Ejemplo: "Trabajo.PDF" pasa a ".pdf".
const extension =
  extname(file.originalname).toLowerCase();

// Comprueba que la extensión esté en nuestra allow-list:
// .pdf, .png, .jpg, .jpeg, .docx, .xlsx.
const extensionIsValid =
  allowedExtensions.includes(extension);

// Comprueba el MIME declarado durante el upload.
// Ejemplo esperado para PDF: application/pdf.
const mimeIsValid =
  allowedMimeTypes.includes(file.mimetype);

// Si falla cualquiera de los dos controles,
// Multer rechaza el archivo y Gateway responde HTTP 400.
if (!extensionIsValid || !mimeIsValid) {
  return callback(
    new BadRequestException(
      'Formato de archivo no permitido',
    ),
    false,
  );
}

Importante: extensión y MIME pueden ser manipulados. Por eso esta validación pertenece al Gateway como filtro inicial, mientras que Upload-MS inspecciona posteriormente los bytes y la estructura real.

3. Generación de UUID

Nombre original:
archivo.pdf

Nombre físico:
4038361e-423f-45b0-9715-88c439a2f3bf.pdf

El UUID evita utilizar directamente el nombre enviado por el usuario como nombre físico del archivo.

// Genera un identificador único controlado por el servidor.
const uuid = randomUUID();

// Conservamos únicamente la extensión previamente permitida.
const extension =
  extname(file.originalname).toLowerCase();

// Construimos el nombre físico.
// Ejemplo:
// 4038361e-423f-45b0-9715-88c439a2f3bf.pdf
const storedName =
  `${uuid}${extension}`;

El usuario no controla el nombre físico del archivo.

4. Cuarentena

gateway/
└── uploads/
    ├── quarantine/
    └── verified/

Todo archivo aceptado inicialmente entra primero en quarantine/. Esa carpeta no debe exponerse como estática ni permitir descarga directa.

Ejemplo: escritura controlada en cuarentena

// process.cwd() apunta al directorio desde donde
// se está ejecutando el Gateway.
//
// join() construye una ruta segura para el sistema operativo.
const quarantinePath = join(
  process.cwd(),
  'uploads',
  'quarantine',
  storedName,
);

// Multer mantiene el archivo temporalmente en memoria.
// Recién después de superar las validaciones iniciales
// escribimos ese buffer en quarantine/.
await writeFile(
  quarantinePath,
  file.buffer,
);

En este punto el archivo existe físicamente, pero continúa siendo no confiable. No debe servirse al usuario desde esta ubicación.

Regla: un archivo en quarantine todavía no está aprobado.

5. Metadata enviada a Upload-MS

Ejemplo: metadata

const metadata = {
  // Identificador interno del upload.
  uuid,

  // Nombre que tenía el archivo en el equipo del usuario.
  originalName: file.originalname,

  // Nombre físico generado por el Gateway.
  storedName,

  // MIME declarado al realizar el upload.
  mimetype: file.mimetype,

  // Tamaño en bytes.
  size: file.size,

  // Ubicación temporal que Upload-MS deberá inspeccionar.
  path: quarantinePath,

  // Momento en que Gateway recibió el archivo.
  uploadedAt: new Date().toISOString(),
};

Gateway utiliza send() porque necesita esperar el resultado del Upload-MS:

Ejemplo: comunicación Gateway → Upload-MS

// send() envía un mensaje TCP y espera una respuesta.
// El patrón "upload: validate" identifica la operación
// que debe ejecutar Upload-MS.
const validationResult = await firstValueFrom(
  this.uploadClient.send(
    { upload: 'validate' },
    metadata,
  ),
);

// firstValueFrom convierte el Observable de ClientProxy
// en una Promise para poder utilizar await.
//
// validationResult contendrá, por ejemplo:
// REJECTED o STRUCTURE_VALIDATED.

Upload-MS escucha con:

@MessagePattern({ upload: 'validate' })

6. Validación 1: firma o magic bytes

Upload-MS lee el archivo desde cuarentena y comprueba la firma PDF:

Ejemplo: inspección de los bytes reales

// Upload-MS abre el archivo que Gateway dejó aislado
// en quarantine/. En este punto ya no confiamos
// solamente en nombre o MIME.
const fileBuffer =
  await readFile(data.path);

// Tomamos los primeros cinco bytes del archivo.
// Un PDF normal comienza con la firma ASCII "%PDF-".
const signature = fileBuffer
  .subarray(0, 5)
  .toString('ascii');

// Si alguien renombró un TXT, BAT u otro archivo como .pdf,
// esta comparación permite detectar que el contenido
// no presenta la firma esperada.
if (signature !== '%PDF-') {
  return {
    status: 'REJECTED',
    reason:
      'La firma del archivo no corresponde a un PDF',
  };
}

Esto permite detectar archivos renombrados como .pdf cuyo contenido real no es PDF.

7. Validación 2: estructura PDF

Una firma correcta no alcanza. Upload-MS intenta interpretar el archivo con pdf-lib:

Ejemplo: validación estructural

// Haber encontrado "%PDF-" no demuestra por sí solo
// que el resto del archivo forme un PDF válido.
//
// pdf-lib intenta interpretar la estructura completa.
const pdf =
  await PDFDocument.load(fileBuffer);

// Si PDFDocument.load() no puede interpretar el documento,
// lanza una excepción y el archivo termina como REJECTED.
//
// Si carga correctamente podemos consultar propiedades
// estructurales, por ejemplo la cantidad de páginas.
const pages =
  pdf.getPageCount();

Esta segunda capa detectó correctamente nuestra prueba falso-estructural.pdf: tenía %PDF-, pero no poseía una estructura PDF válida.

Si la estructura no puede interpretarse como PDF, se devuelve:

{
  "status": "REJECTED",
  "reason": "La estructura interna del PDF no es válida"
}

Si pasa firma y estructura:

{
  "detectedType": "PDF",
  "signature": "%PDF-",
  "pages": 4,
  "status": "STRUCTURE_VALIDATED"
}

8. Archivo rechazado

Si Upload-MS responde REJECTED, el Gateway elimina el archivo físico de cuarentena.

Ejemplo: eliminación de un archivo rechazado

// Upload-MS no elimina archivos.
// Solamente informa el resultado de su análisis.
//
// Gateway sigue siendo el propietario del almacenamiento.
if (validationResult.status === 'REJECTED') {

  // unlink() elimina físicamente el archivo
  // que había quedado temporalmente en quarantine/.
  await unlink(quarantinePath);

  console.log(
    'Archivo rechazado y eliminado de cuarentena:',
  );
  console.log(quarantinePath);
}

9. Archivo estructuralmente válido

Para el alcance actual del prototipo, cuando Upload-MS devuelve STRUCTURE_VALIDATED, el Gateway mueve el archivo de cuarentena a verified/.

Ejemplo: salida de cuarentena

// Preparamos la ubicación final para los archivos
// que superaron las validaciones implementadas.
const verifiedPath = join(
  process.cwd(),
  'uploads',
  'verified',
  storedName,
);

// Upload-MS devuelve STRUCTURE_VALIDATED cuando:
// 1) la firma corresponde a PDF;
// 2) pdf-lib puede interpretar su estructura.
if (
  validationResult.status === 'STRUCTURE_VALIDATED'
) {

  // rename() mueve el archivo desde quarantine/
  // hacia verified/. El Gateway realiza el movimiento
  // porque es quien administra el almacenamiento físico.
  await rename(
    quarantinePath,
    verifiedPath,
  );

  console.log(
    'Archivo validado y movido a verified:',
  );
  console.log(verifiedPath);
}
STRUCTURE_VALIDATED
        |
        v
     Gateway
        |
     rename()
        |
        v
quarantine/UUID.pdf
        |
        v
verified/UUID.pdf
Aclaración: el estado sigue llamándose STRUCTURE_VALIDATED porque las validaciones implementadas hasta ahora son firma y estructura. La carpeta verified/ representa la zona aprobada para el alcance actual del prototipo.

12. Responsabilidades actuales

ComponenteResponsabilidad
Gateway Recibir HTTP, Multer, validar tamaño/extensión/MIME, generar UUID, guardar en cuarentena, enviar metadata por TCP, eliminar rechazados y mover aprobados a verified.

14. Flujo de estados y respuesta entre Gateway y Upload-MS

El Gateway y Upload-MS se comunican mediante TCP usando el patrón send() / @MessagePattern(). El Gateway inicia la solicitud de validación y queda esperando la respuesta del microservicio.

Frontend
   |
   v
Gateway
   |
   | 1. recibe archivo
   | 2. valida tamaño / extensión / MIME
   | 3. genera UUID
   | 4. guarda en quarantine
   |
   | 5. send({ upload: 'validate' }, metadata)
   v
Upload-MS
   |
   | 6. lee archivo
   | 7. valida firma
   | 8. valida estructura
   |
   | 9. genera resultado
   |    REJECTED
   |       o
   |    STRUCTURE_VALIDATED
   |
   | 10. return resultado
   v
Gateway
   |
   | 11. recibe resultado
   |
   +-- REJECTED ----------> unlink()
   |
   +-- STRUCTURE_VALIDATED -> rename()

Gateway: envío y espera de respuesta

El Gateway utiliza send() porque necesita conocer el resultado antes de decidir qué hacer con el archivo físico.

// Gateway envía la metadata al Upload-MS.
// El patrón identifica la operación que debe ejecutar.
const validationResult = await firstValueFrom(
  this.uploadClient.send(
    { upload: 'validate' },
    metadata,
  ),
);

// firstValueFrom transforma el Observable de ClientProxy
// en una Promise para poder esperar la respuesta con await.
//
// Mientras Upload-MS analiza el archivo, Gateway
// permanece esperando este resultado.

La correspondencia entre ambos servicios es:

Gateway                                  Upload-MS

send({ upload: 'validate' })  -------->  @MessagePattern({
                                           upload: 'validate'
                                         })

Upload-MS: momento en que genera el estado

Upload-MS genera el estado durante la validación, justo antes de responder al Gateway.

Si falla la firma:

if (signature !== '%PDF-') {
  return {
    uuid: data.uuid,
    status: 'REJECTED',
    reason:
      'La firma del archivo no corresponde a un PDF',
  };
}

Ese return ya constituye la respuesta TCP que vuelve al Gateway.

Si la estructura PDF es inválida:

catch (error) {
  return {
    uuid: data.uuid,
    status: 'REJECTED',
    reason:
      'La estructura interna del PDF no es válida',
  };
}

Si supera ambas validaciones:

return {
  uuid: data.uuid,
  detectedType: 'PDF',
  signature,
  pages,
  status: 'STRUCTURE_VALIDATED',
};

Gateway: decisión física sobre el archivo

El Gateway recibe el objeto devuelto por Upload-MS en validationResult y actúa sobre el archivo físico.

// Si Upload-MS decide que el archivo no es válido,
// Gateway elimina el archivo de quarantine.
if (validationResult.status === 'REJECTED') {
  await unlink(quarantinePath);
}

// Si Upload-MS confirma firma y estructura,
// Gateway mueve el archivo a verified.
if (
  validationResult.status === 'STRUCTURE_VALIDATED'
) {
  await rename(
    quarantinePath,
    verifiedPath,
  );
}

La separación de responsabilidades queda así:

UPLOAD-MS
    |
    | decide estado
    v
REJECTED / STRUCTURE_VALIDATED
    |
    | respuesta TCP
    v
GATEWAY
    |
    | actúa sobre archivo físico
    |
    +--> unlink()
    |
    +--> rename()
Principio de diseño:

El Gateway es propietario del archivo físico. Upload-MS es propietario de la decisión de validación. Upload-MS no borra ni mueve archivos: informa el resultado. Gateway interpreta ese estado y ejecuta la acción correspondiente sobre quarantine/ o verified/.

Flujo futuro con MongoDB

Gateway

Upload-MS

Esto permitirá conservar trazabilidad incluso cuando el archivo rechazado ya haya sido eliminado físicamente.

Conclusión:

El flujo implementado demuestra que extensión y MIME no bastan. El Gateway aplica controles rápidos y conserva el archivo físico; Upload-MS inspecciona el contenido real. Si la firma o la estructura PDF fallan, el archivo se elimina. Si ambas validaciones pasan, el Gateway lo mueve desde cuarentena a la zona verified/.
